# Known limitations

What UndoKit does not do, or does with a caveat, at the time of writing. Each item has a severity and the
mitigation an operator can apply today. Severity: P2 means wrong or misleading behavior with a workaround; P3
means minor or hardening. Items that were found and fixed are recorded as defects in `docs/qa/AC-MATRIX.md`, not
here. This is a list of things that are still true.

Read with `docs/qa/AC-MATRIX.md`: the live provider drill (AC-07) has not been run and the documentation drill
(AC-11) is waiting for a human receipt.

## Behavior

| Item | Severity | What happens | Mitigation |
| --- | --- | --- | --- |
| Applied with a read-back mismatch | P2 | If the provider stores a different value at UndoKit's own write version (`mismatch`) or a later edit by someone else is seen on read-back (`changed_other`), the attempt is still recorded as succeeded and the operation state is `applied`. Only the per-field outcome and the report flag it. A consumer that keys on `state == applied` alone will treat it as success. | Read the per-field outcomes (`apply_outcome`) and the report, not just the state. Treat any field that is not `applied` as needing a human decision. |
| Resolving an UNKNOWN by hand is an assertion, not proof | P3 | An administrator can close an UNKNOWN operation with `POST /api/v1/operations/{id}/resolve` (`not_applied` or `abandoned`, with a reason). It is recorded and attributed but not verified: UndoKit never consults the provider for it. A late write still reopens the operation (`LATE_RESULT`). | Check the provider first and write a useful reason; review `apply.operator_resolved` events. |
| Idempotency-Key is ignored on approve, compensate and reconcile | P3 | The header is honored when planning. On approve, compensate and reconcile it is ignored, so a retried approve returns 409 `INVALID_STATE` instead of the original receipt. The state was still applied exactly once. | On a 409 after a retry, read the operation: if it is already approved, it is. Do not approve again. |
| The worker does not restart after readiness flips back | P3 | Readiness returns only when `/ready` is called, and the in-process worker is started only if the server was ready at boot. After a migration is fixed or a database blip clears, the API can report ready while no worker is running. | After any readiness incident, restart `undokit serve`. |
| Bundle integrity is tamper-evident only | P2 | Verification checks that a bundle is self-consistent (hash chain, manifest and bundle hashes). There is no signature or authentication. Someone who edits a value **and recomputes every hash** produces a bundle that `verify` and `import` accept and that the report renders; the operation's plan hash and field value hashes are not re-checked against the values. Imported operations also merge into `undokit report` without a per-operation provenance marker. | Treat a bundle as proof against damage and naive edits only, not as proof of origin. Import only bundles from sources you trust and record where each came from. |
| CLI data commands need the daemon stopped | P3 | With the embedded database, `report`, `export` and `import` on a data directory fail ("in use by process N") while `serve` runs on it; `report` writes an error-state report. | Stop the daemon first, or use `GET /status` and `POST /api/v1/exports` while it runs. |
| Reconcile with an unreachable provider does not fail loudly | P3 | The request returns 202, the job finishes, and the operation stays `unknown`; the only trace is the evidence event `reconcile.indeterminate` (`CONNECTOR_UNAVAILABLE`). `/status` text does not change. | Check the operation's events after requesting reconciliation; fix the connection and ask again. |
| An administrator can allowlist any field name | P3 | The send/delete classifier only runs for fields that are not allowlisted, so an admin can allowlist names like `send_email` or `delete`, and plans on them are accepted. The allowlist is administrator-controlled policy. | Review the allowlist when creating a connector; only administrators can change it. |
| `demo --out` overwrites | P3 | `undokit demo --out <existing dir>` silently overwrites `report.html` and `evidence.json` there. | Use a new or empty directory. |
| Workspace isolation is reachable only through the library | P3 | A second workspace cannot be created through the shipped CLI or API (`createWorkspaceWithAdmin` is library-only), so an operator of the shipped product cannot exercise cross-workspace isolation; it is tested through the library. Compensation approval is by the same operator and session class by design (no four-eyes). | Run one workspace per installation; require a second person for compensation by process, not by software. |
| Provider data visible to viewers | P3 | Viewers can read connector `base_url` and the field policy (not credentials). | Do not put anything sensitive in a connector's name or URL. |
| The simulator is in-memory | P3 | The built-in simulator re-seeds from its configuration on every start. It is test infrastructure and is never a live provider. | Use a real provider for anything but the demo and tests. |
| `demo --data-dir` is parsed and ignored | P3 | The flag is accepted by `undokit demo` but the demo is always self-contained and writes only to `--out`. | Use `--out`. |
| `startServer.close()` does not wait for an in-flight worker tick | P3 | Stopping the server while a job is running ends the process with the job in flight. The attempt is recovered as `unknown` by lease expiry. | Stop the daemon when no job is running (the upgrade procedure already says so). |
| Migrations take no cross-process lock | P3 | Two processes starting against one PostgreSQL database at the same moment could both try to migrate. | Start one process first and wait for `/ready` before starting others. |

## Security hardening

| Item | Severity | What happens | Mitigation |
| --- | --- | --- | --- |
| Outbound allowlist gaps | P3 | IPv4-mapped IPv6 link-local or metadata addresses and `100.64.0.0/10` are not blocked, and the DNS check and the connection resolve the name separately (a rebinding window). Exploiting this needs an attacker-controlled DNS name that the operator has already allowlisted. | Allowlist only host names and addresses you control. Prefer literal IPs for loopback and private providers. |
| The test harness does not patch `dns.promises.lookup` | P3 | The outbound-deny preload used in tests patches the connection primitives but not `dns.promises.lookup`, so a name lookup is not recorded as an attempt. This weakens the harness, not the product. | None needed for operators. |

## Backup, retention and operations

| Item | Severity | What happens | Mitigation |
| --- | --- | --- | --- |
| The key file is inside the data directory by default | P2 | Unless you set `UNDOKIT_KEY_FILE` or `UNDOKIT_ENCRYPTION_KEY`, a `tar` of the data directory includes the encryption key. | Set `UNDOKIT_KEY_FILE` to a path outside the data directory (honored with `--data-dir`) or use `UNDOKIT_ENCRYPTION_KEY`, and keep it under separate custody. Treat the archive as secret otherwise. (`docs/OPERATIONS.md` 5.0) |
| The documented backup is not tested | P2 | The `tar` procedure in `docs/OPERATIONS.md` is not exercised by any automated test. `backupDatabase` and `restoreDatabase` are tested but have no CLI command. There is no tested PostgreSQL backup procedure. | Test your own restore into a scratch location before relying on it, and reconcile after every restore. |
| No retention or deletion | P2 | Nothing expires. Evidence tables are append-only and there is no configurable retention window or "delete within 24 hours" mechanism. Blob bundles and a capacity pre-check do not exist either. | Decide the policy before ingesting customer data; deleting means removing the whole data directory and its backups. Use synthetic data until then. |
| No application logger | P3 | UndoKit writes no request or application log. Credentials and sensitive values are redacted in API responses, evidence and reports; "personal field log redaction" is not implemented because there is nothing to redact. | Rely on the evidence events and `GET /status`. Protect your reverse proxy and supervisor logs. |
| The Dockerfile is unverified | P3 | `Dockerfile` has not been built or run (the container engine was unavailable) and `compose.yaml` defines only the local provider sandbox. | Run the daemon with `npx undokit serve`. |
| Unit and integration tests are not type-checked | P3 | `tsconfig.json` covers `src` only, so `npm run typecheck` does not check files under `tests/`. Type errors in the test helpers are possible and invisible to the gate. | Tests run under vitest; review test changes by reading them. |

## Proof status

| Item | Severity | What happens | Mitigation |
| --- | --- | --- | --- |
| The quality gate exits 0 with AC-07 NOT RUN | P3 | `scripts/verify-quality.sh` exits 0 when every automated step passes, even though the live provider drill (AC-07) was not run and AC-11 is pending a human receipt. The verdict text says `GREEN-LOCAL` and "NOT a claim that the AC matrix passed", but a wrapper that looks only at the exit code sees a pass. | Read the verdict line and the receipt's step table, not only the exit code. Do not describe a `GREEN-LOCAL` run as release-ready. |
| The PRD performance benchmark is not recorded | P3 | A measurement of plan, approve and apply over 100 operations gave about 5.5 ms each in review, but no benchmark is recorded in the repository. | Measure on your own hardware before depending on throughput. |
| No live provider drill yet | P2 | AC-07 is NOT RUN. The CouchDB connector has been exercised only by an in-process protocol test (labelled not live) and a builder's smoke run, neither of which counts. | Run the opt-in drill with the local sandbox (`docs/qa/AC-MATRIX.md`, AC-07) before trusting a live connector. |

## Concurrency, clocks and operations

| Item | Severity | What happens | Mitigation |
| --- | --- | --- | --- |
| A provider-side delay after the client gave up | P3 | If a PUT was sent, the client timed out, and the provider (or a proxy queue in front of it) commits that PUT later than the lease plus one connector deadline (43.5 s by default) after the attempt started, reconciliation may already have concluded `failed` (`NOT_APPLIED`) and no worker result will ever arrive to reopen it. The provider's compare-and-set still prevents any overwrite, but the evidence for that operation would be wrong. | Keep `timeout_ms` well below the provider's own request timeout, and compare the provider's current state when an unexpected change shows up on a record with a `NOT_APPLIED` operation. |
| No maximum job runtime | P3 | The worker renews its lease while a job runs, so a handler that wedges (for example on a database lock) keeps its lease for as long as the process lives. The operation stays `applying` and no other change can be planned on that record until the process restarts. | Restart `undokit serve`; the attempt is recovered as `unknown` and reconciled. |
| Lease arithmetic uses each process's own clock | P3 | The lease, heartbeat and quiet period use the application clock of each worker, not the database clock. Clock skew between hosts of more than about a third of the lease (10 s by default) can cause an early reclaim, and different `UNDOKIT_LEASE_SECONDS` values across processes shorten one process's quiet period relative to another's lease. Fencing and the quiet period contain the damage. | Run time synchronization on every host and give every process the same lease setting. |
| The consistent backup snapshot is verified on the embedded database only | P3 | `backupDatabase` reads all tables in one `REPEATABLE READ READ ONLY` transaction. This was tested on PGlite. The statement is standard PostgreSQL and no PostgreSQL run was recorded; it also holds every table's rows in memory at once. | Test a backup and restore on your own PostgreSQL before relying on it. |
| An apply job that fails before dispatch leaves the operation approved | P3 | If the apply job fails in its first transaction (for example a decryption error), the operation stays `approved` with a failed job, and there is no re-approve or invalidate action. The status view lists it as approved with no apply job queued. | Restart the daemon; if the cause persists, plan the change again from the record's current version. |
| The data-directory lock identifies holders by pid and host name | P3 | The lock file holds `<pid> <host name>` and is touched every 5 s. Two containers that share one volume, have the same explicitly configured host name and the same pid look like one container restarting and could take the lock over. A container recreated after a crash has a new host name and waits up to 30 s for the dead holder's heartbeat to age out. Heartbeat freshness assumes machines sharing a network volume agree on the time to within 30 s. | Give each container its own host name and do not share the embedded database's volume between running instances. |
| Lock creation and cross-host heartbeat limits | P3 | The embedded database is meant for one container. The lock file is created atomically, but its liveness across hosts rests on a heartbeat every 5 s, a 30 s staleness window, and clocks that agree within that window. A clock jump or a long pause can look like a dead holder. | For anything shared between containers or hosts use PostgreSQL, not the embedded database. |
| A full login-limiter table | P3 | The failed-login limiter keeps at most 10,000 keys. When every key in a full table is locked out, a new key can evict a locked one, so a flood of distinct locked-out keys could release the oldest lockout early. Unlocked entries are evicted first. | Put a rate limit in front of the daemon (your reverse proxy); the in-process limiter is a second line. |
| A proxy address list must contain proxies only | P3 | `UNDOKIT_TRUST_PROXY` accepts a hop count or a list of proxy addresses/CIDRs. A list that includes client ranges would trust a client's own `X-Forwarded-*` headers. | Prefer the hop count; if you use a list, put only your proxies' addresses in it. |
